# ADR-002: Модульная архитектура NestJS

**Статус:** принято · **Дата:** 2026-10-23

## Проблема

Исходный backend — 18 файлов Next.js Route Handlers, в каждом смешаны проверка сессии, валидация, запросы к БД и формирование ответа. Логику нельзя переиспользовать и тестировать отдельно.

## Рассмотренные варианты

1. Оставить Route Handlers в Next.js.
2. Express без фреймворка.
3. **NestJS** с модулями, контроллерами, сервисами и DTO.

## Принятое решение

NestJS 11. Каждая предметная область — отдельный модуль: `auth`, `users`, `profiles`, `posts`, `comments`, `likes`, `follows`, `stories`, `reels`, `feed`, `search`, `messages`, `notifications`, `media`, `privacy`, `sessions`, `settings`, плюс служебные `realtime`, `mail`, `health`, `prisma`, `common`.

- **Controller** — только HTTP: маршрут, DTO, текущий пользователь, вызов сервиса.
- **Service** — бизнес-логика и Prisma-запросы.
- **DTO** (class-validator) — проверка входных данных; глобальный `ValidationPipe` с `whitelist` и `forbidNonWhitelisted`.
- Глобальный `JwtAuthGuard`: все маршруты защищены, публичные помечаются `@Public()`.
- `VisibilityService` (модуль `privacy`) — единая точка проверки «может ли пользователь X видеть контент пользователя Y» (блокировки, приватный аккаунт, подписка).
- `DtoMapper` / `MediaUrlService` — единообразное превращение строк БД в ответы API.

## Причины выбора

- NestJS требует указанный стек и даёт понятную структуру, которую легко объяснить новичкам.
- Сервисы можно тестировать отдельно и переиспользовать (например, `NotificationsService` вызывается из лайков, комментариев, подписок, сообщений).

## Последствия

- Больше файлов, чем в исходнике, но каждый файл маленький и отвечает за одно.
- Новый модуль добавляется по одному и тому же шаблону: `*.module.ts`, `*.controller.ts`, `*.service.ts`, `dto/*.dto.ts`.
