# Объяснения простым языком

Этот файл для двух разработчиков, которые только начинают. Здесь — «почему так», без сложных слов.

## 1. Как устроен проект

```text
instagram-project/
├── apps/api        ← сервер (NestJS). Хранит данные, проверяет права.
├── apps/web        ← сайт (Next.js). То, что видит пользователь.
├── packages/shared ← общие правила и типы для api и web
└── docs/           ← решения (ADR), ТЗ, спецификации модулей
```

Это **monorepo**: всё в одной папке и одном git-репозитории. Одна команда `npm install` в корне ставит зависимости для всех частей. Если поменять правило пароля в `packages/shared`, оно поменяется и на сервере, и на сайте.

## 2. Путь запроса на сервере

Пример: пользователь лайкает пост.

1. Браузер отправляет `POST /api/posts/<id>/like` с заголовком `Authorization: Bearer <access token>`.
2. **Guard** (`JwtAuthGuard`) проверяет токен. Нет токена → 401.
3. **Controller** (`likes.controller.ts`) получает id поста и текущего пользователя и вызывает сервис. Больше он ничего не делает.
4. **Service** (`likes.service.ts`) проверяет, можно ли видеть этот пост (`VisibilityService`), создаёт запись `Like`, увеличивает `likesCount`, просит `NotificationsService` создать уведомление.
5. **Prisma** превращает вызовы в SQL для PostgreSQL.

Правило: контроллер — «администратор у входа», сервис — «мастер, который делает работу».

## 3. DTO — проверка входящих данных

DTO — это класс с правилами для полей (`@IsEmail()`, `@MaxLength(150)`). Если клиент прислал лишнее поле или неправильное значение, NestJS сам ответит 400 ещё до сервиса. Поэтому никто не может «подсунуть» поле `isVerified: true`.

## 4. Вход и токены — самое важное

У пользователя два токена:

| Токен | Где живёт | Сколько живёт | Зачем |
|---|---|---|---|
| **access** | в памяти браузера (Redux) | 15 минут | прикладывается к каждому запросу |
| **refresh** | в cookie `rt`, которую JavaScript **не видит** (`httpOnly`) | 30 дней | получить новый access |

Почему так: если злоумышленник как-то запустит свой скрипт на странице, он не сможет прочитать refresh-cookie. А украденный access проживёт максимум 15 минут.

**Ротация.** Каждый раз, когда сайт обновляет access, сервер выдаёт **новый** refresh, а старый помечает «использован». Если кто-то придёт со старым refresh — значит, его украли и пытаются использовать второй раз. Сервер тогда закрывает всю сессию.

**В базе refresh-токены хранятся только как хеш** (`sha256`). Даже если базу украдут, токенами воспользоваться нельзя. Пароли — тоже только хеш (`bcrypt`).

**Сессия** = одно устройство. Можно посмотреть список (`GET /api/sessions`) и закрыть чужое устройство.

**Защита от перебора паролей:** 5 неверных попыток — аккаунт закрыт для входа на 15 минут; кроме того, с одного адреса не больше 10 попыток в минуту.

## 5. Frontend: кто за что отвечает

- **Axios** (`lib/http.ts`) — просто «почтальон»: отправляет HTTP-запросы.
- **RTK Query** (`store/api.ts`) — «память» сайта: хранит ответы сервера, показывает загрузку и ошибки, обновляет данные после изменений.
- **authSlice** (`store/auth-slice.ts`) — хранит только access token и статус (`unknown` / `authenticated` / `guest`).
- **baseQuery** (`store/base-query.ts`) — если сервер ответил 401 (access истёк), он один раз обновляет токен и повторяет запрос. Пользователь ничего не замечает.
- **refreshSession** (`lib/refresh-session.ts`) — гарантирует, что одновременно идёт только **один** запрос на обновление. Иначе два одновременных refresh сервер принял бы за кражу (см. п. 4).

Когда страница открывается, `AuthBootstrap` пробует обновить токен по cookie. Получилось — пользователь вошёл. Нет — он гость.

`RequireAuth` пускает на страницу только вошедших, `GuestOnly` — только гостей (вошедшего с `/login` отправит на главную `/`).

## 7. Приватность и блокировки

Вся логика «кто что может видеть» собрана в одном месте — `VisibilityService`:
- если один заблокировал другого — они не видят друг друга;
- приватный аккаунт показывает посты только подписчикам;
- настройки «кто может комментировать / упоминать / писать» — `EVERYONE` (все), `FOLLOWERS` (мои подписчики), `FOLLOWING` (люди, на которых **я** подписана), `NO_ONE` (никто).

Одно место = меньше шансов забыть проверку в новом endpoint.

**Главное правило: проверяет сервер, а не сайт.** Сайт может спрятать кнопку, но хитрый пользователь отправит запрос сам (через Postman или консоль). Поэтому каждое правило проверяется на backend, а e2e-тесты (`test/privacy.e2e-spec.ts`) это доказывают: тест «стучится» в API от имени чужого человека и ждёт отказ (403/404).

Как это работает на примерах:

| Ситуация | Что делает сервер |
|---|---|
| Закрытый аккаунт, вы не подписаны | Посты, reels, stories профиля → 403; пост по прямой ссылке → 404 |
| Подписка на закрытый аккаунт | Создаётся **запрос**; владелец принимает или отклоняет на странице уведомлений |
| Блокировка | Подписки, запросы и «Близкие друзья» удаляются в обе стороны; профиль, посты, подписка, сообщения → 404/403; блок виден в Настройки → Заблокированные |
| «Писать могут только мои подписки» | Проверяется при создании диалога **и при каждом сообщении** — даже в старом диалоге |
| Story «Только подписчики» / «Близкие друзья» | Чужие не получают её в ленте, а отметить просмотр по id → 404 |
| «Скрыть stories от …» | Этот человек не видит ни одной вашей story |
| Жалоба | Сохраняется в таблицу `Report` (причина из списка). Повторная жалоба на то же → 409. Админ-панели пока нет |

Как фильтр для stories выглядит в коде: `VisibilityService.storyVisibleWhere(viewerId)` возвращает условие для Prisma («автор — я, ИЛИ (нет блокировки И автор не скрыл от меня И аудитория разрешает)»). Это условие добавляется ко всем запросам stories, поэтому забыть его сложно.

## 8. Файлы (фото, видео, голос)

Файлы **не кладём в базу** (в исходном проекте картинки хранились в базе как длинный текст base64 — это очень медленно). Сейчас:

1. Сначала файл загружается: `POST /api/media` → получаем `id`.
2. Потом `id` передаётся в пост, story или сообщение.
3. Сервер проверяет **настоящий** тип файла по первым байтам (а не по имени `.jpg`), размер, и пересохраняет картинки через Sharp — это заодно удаляет скрытые данные, например GPS-координаты.
4. Ссылка на файл подписана и живёт 1–2 часа, поэтому чужое фото из приватного аккаунта нельзя открыть по старой ссылке навсегда.

## 9. Realtime (сообщения «вживую»)

Socket.io держит постоянное соединение. При подключении сервер проверяет access token — в исходном проекте сервер просто верил присланному `userId`, и можно было писать от чужого имени. Каждый пользователь попадает в свою «комнату» `user:<id>`, и сервер отправляет события только участникам диалога.

Для видеозвонков сервер лишь передаёт «служебные записки» WebRTC между двумя людьми (offer/answer/ICE). Само видео идёт напрямую между браузерами.

**Во frontend** сокет подключает `RealtimeProvider` (`components/providers/realtime-provider.tsx`). Он не хранит данные сам — он только говорит RTK Query «эти данные устарели» (инвалидация тегов):

- пришло `notification:new` → обновить список и счётчик уведомлений;
- пришло `message:new` → обновить бейдж «Сообщения» и контакты;
- `presence:online` / `presence:offline` → поменять зелёную/серую точку у контакта прямо в кэше.

Так у нас по-прежнему **один** кэш данных (RTK Query), а сокет — только «звонок в дверь».

## 9.1. Светлая и тёмная тема

- Все цвета — **токены** (CSS-переменные) в `src/app/globals.css`: блок `:root` — светлая тема, блок `.dark` — тёмная. В компонентах пишем `bg-surface`, `text-link`, `btn-follow`, а не `#0095f6`. Чтобы поменять цвет, меняем одну строку в `globals.css`.
- Выбор пользователя (`light` / `dark` / `system`) хранится в `localStorage`. Чтение и запись обёрнуты в `try/catch`: в приватном режиме браузер может запретить хранилище, и сайт не должен падать.
- **Почему нет мигания.** React запускается не сразу. Если ставить тему из React, страница сначала покажется светлой, а потом «моргнёт» в тёмную. Поэтому в `<head>` есть маленький скрипт (`themeInitScript` в `lib/theme.ts`): он выполняется **до** отрисовки и сразу ставит класс `dark` на `<html>`.
- Переключатель — в меню аватара (справа сверху).

## 9.2. Общий layout

`AppShell` (`components/layout/app-shell.tsx`) = сайдбар слева + центр + правая колонка.

- **Компьютер (≥ 1280 px):** 3 колонки.
- **Планшет (768–1279 px):** правая колонка скрыта; на узком планшете в сайдбаре только иконки.
- **Телефон (< 768 px):** сверху логотип и иконки, снизу панель навигации.

Правая колонка берёт данные только из API: `/auth/me`, `/users/suggested`, `/users/me/contacts`. Никаких имён и фото из макета в коде нет.

**Оптимистичное обновление (кнопка «Подписаться»).** Кнопка меняется сразу, не дожидаясь сервера. Если сервер ответил ошибкой — возвращаем как было и показываем сообщение. Так интерфейс кажется быстрым.

## 9.3. Как работает realtime (простыми словами)

1. После входа сайт открывает **одно** соединение Socket.io (`lib/socket.ts`) и отдаёт серверу access token. Сервер проверяет токен и сажает пользователя в его «комнату» `user:<id>`.
2. Когда что-то происходит, сервер **сам** отправляет событие в нужную комнату:
   - кто-то лайкнул / прокомментировал / упомянул / подписался → `notification:new` автору;
   - новое сообщение → `message:new` участникам диалога;
   - человек печатает → `typing`; прочитал → `conversation:read`; реакция → `message:reaction`;
   - вошёл / вышел → `presence:online` / `presence:offline` собеседникам.
3. `RealtimeProvider` получает событие и **не хранит его сам**, а говорит RTK Query: «обнови счётчик» (инвалидация тега) или точечно меняет кэш (новое сообщение, реакция, зелёная точка). Поэтому бейдж у сердца и в сайдбаре меняется без перезагрузки.
4. Сообщения отправляются обычным REST-запросом (`POST /conversations/:id/messages`) — там все проверки (блокировка, кто может писать). Сокет только **доставляет** результат. Так проверки не дублируются.

«Доставлено» = сервер сохранил сообщение. «Прочитано» = собеседник открыл чат (его `lastReadAt` позже сообщения). Если он выключил «Отчёты о прочтении», вы увидите только «Доставлено».

## 9.4. Голосовые сообщения

Браузер записывает звук через `MediaRecorder` (формат WebM/Opus, в Safari — MP4). Мы отправляем файл в `POST /media` (purpose `MESSAGE`), сервер проверяет «магические байты» файла (что это правда аудио) и размер, а потом сообщение типа `AUDIO` с этим файлом. На сервере нет нативных модулей для звука — только проверка и сохранение. Микрофон браузер даёт только на `localhost` или по HTTPS.

## 9.5. Уведомления

- Создаёт их **только сервер** (лайк, комментарий, подписка, запрос, упоминание `@username` в посте или комментарии). Упоминания ищутся в тексте на backend (`TaggingService`).
- В настройках можно выключить каждый тип — сервер просто не создаст уведомление.
- Страница `/notifications` делит список на «Сегодня» и «Ранее», умеет «прочитать одно» и «прочитать все», показывает запросы на подписку с кнопками «Подтвердить / Удалить».
- Уведомления о сообщениях в этот список не попадают: у сообщений свой бейдж.

## 9.6. Бесконечная прокрутка (cursor pagination)

Сервер отдаёт страницу `{ items, nextCursor }`. Когда пользователь доходит до конца, невидимый элемент внизу (`LoadMore`, IntersectionObserver) просит следующую страницу с `?cursor=…`. В RTK Query это `build.infiniteQuery`: все страницы лежат в одном кэше.

## 9.7. Анимации

- Все анимации описаны в `src/app/globals.css` в блоке `@theme`: например `--animate-like-pop` превращается в класс `animate-like-pop`.
- Анимируем только `transform` (сдвиг, масштаб, поворот) и `opacity` (прозрачность): браузер делает это на видеокарте, страница не «прыгает».
- Чтобы анимация проигралась ещё раз, у элемента меняется `key` — React создаёт его заново, и CSS-анимация начинается сначала (так работают сердце, счётчик, бейдж).
- Меню и модальные окна при закрытии сначала проигрывают анимацию 150 мс, а потом исчезают (`components/ui/use-presence.ts`).
- Если в системе включено «Уменьшить движение» (`prefers-reduced-motion`), CSS сокращает все анимации почти до нуля.
- Смена темы: на 350 мс на `<html>` ставится класс `theme-transition`, и цвета меняются плавно. При загрузке страницы этого класса нет — поэтому мигания нет.

## 9.8. Демо-данные (seed)

- `npm run db:seed` запускает `apps/api/prisma/seed.ts`. Он поднимает NestJS **без HTTP-сервера** (`createApplicationContext`) и вызывает те же сервисы, что и API: файлы проходят проверку типа, Sharp и попадают в обычное хранилище. Поэтому демо-данные ничем не отличаются от настоящих.
- **Пометка демо-данных** — почта `@demo.insta.local`. Reset удаляет только таких пользователей; всё, что они создали (посты, лайки, комментарии, подписки), удаляется каскадом, а файлы — из хранилища.
- **Идемпотентность**: перед созданием seed проверяет, есть ли уже такой пользователь / пост с той же подписью / reel / активная story / комментарий. Поэтому повторный запуск ничего не дублирует, а только дополняет (например, свежие stories через 24 часа или новые видео).

## 9.9. Звонки (WebRTC)

Голос и видео идут **напрямую между браузерами** (WebRTC), а не через наш сервер. Сервер нужен только чтобы браузеры «познакомились» — это называется сигналинг:

1. Звонящий берёт камеру/микрофон (`getUserMedia`), создаёт `RTCPeerConnection` и отправляет описание соединения (SDP) событием `call:offer`.
2. Сервер проверяет токен, блокировки и «кто может мне писать», добавляет имя и аватар звонящего и пересылает событие получателю.
3. Получатель нажимает «Принять» и отвечает `call:answer`. Обе стороны обмениваются адресами (`call:ice-candidate`), и дальше звук и видео идут напрямую.

STUN-сервер Google помогает браузеру узнать свой внешний адрес. Через интернет, когда оба за роутерами, этого часто мало — нужен TURN-сервер (ретранслятор), он в ROADMAP.

Почему кнопки «выключить камеру» не трогают сервер: состояние камеры и микрофона отправляется по `RTCDataChannel` прямо собеседнику, и он показывает аватар вместо чёрного экрана.

Почему камера работает только на `localhost` или HTTPS: так решили браузеры — сайт по обычному `http://192.168…` камеру и микрофон не получит.

Код: `apps/web/src/components/calls/` (`call-provider.tsx` — логика, `call-screen.tsx` — экран звонка, `incoming-call.tsx` — входящий, `call-media.ts` — камера/микрофон и понятные ошибки).

## 10. Тесты

- **Unit** (`src/**/*.spec.ts`) — проверяют маленькие функции: подпись ссылок, разбор хэштегов, пагинацию.
- **E2E** (`test/*.e2e-spec.ts`) — поднимают настоящий сервер и настоящую тестовую базу и проверяют сценарии целиком: «зарегистрировался → вошёл → украл токен → сервер закрыл сессию».

Правило команды: в документах пишем «тесты прошли» **только** если их действительно запустили.

**Важно про базу для e2e.** Перед каждым набором e2e-тесты **очищают все таблицы** (`TRUNCATE`). Поэтому им нужна отдельная база, имя которой заканчивается на `_test` (у нас `insta_clone_test`), и файл `apps/api/.env.test`. Если файла нет или имя базы без `_test`, `test/setup-env.ts` сразу останавливает тесты — так рабочая база `insta_clone` не может случайно стереться.

## 10.1. Что сделано (для защиты проекта)

- **Лента**: посты подписок, бесконечная прокрутка, stories сверху.
- **Пост**: до 10 фото/видео, карусель «1/5» с точками, лайк (сразу, без ожидания сервера), комментарии, сохранение, удаление своего, жалоба на чужой.
- **Профиль**: статистика, вкладки Posts / Reels / Saved, «Подписаться / Отписаться», «Написать», блок, жалоба, закрытый аккаунт.
- **Stories**: кружки (цветные — не просмотрено, серые — просмотрено), просмотрщик с полосками и переключением, аудитория, 24 часа.
- **Reels**: вертикальная лента, автоплей видимого видео, лайк, комментарии.
- **Поиск** (задержка 300 мс, история в браузере) и **Интересное** (популярное от неподписанных, хэштеги).
- **Уведомления**, **Настройки** (приватность, уведомления, близкие друзья, скрытие stories, заблокированные), **Сообщения** (текст, фото, голос, реакции, «печатает…», онлайн, прочитано).
- Всё в светлой и тёмной теме, на телефоне — нижняя панель, на трёх языках.

- **Звонки** 1:1 — аудио и видео прямо из чата (WebRTC).

Чего пока нет — TURN-сервера: звонки работают на одном компьютере и в одной сети, но не через интернет. Это в ROADMAP.

## 11. Как добавить новую функцию

1. Посмотреть, нет ли её уже в `docs/SPEC` и Swagger.
2. Если меняется схема БД: изменить `schema.prisma` → `npm run db:migrate`.
3. DTO → сервис → контроллер в нужном модуле.
4. E2E-тест.
5. Обновить SPEC, ROADMAP, PROGRESS.
6. Если решение меняет архитектуру — сначала ADR.
